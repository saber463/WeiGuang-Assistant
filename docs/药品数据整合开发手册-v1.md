# 药品数据整合开发手册 v1.0

## 1. 文档用途

这份文档是给微光畅行项目直接落开发用的整合手册，目标是一次性解决 5 件事：

1. 把 4 个药品数据源拆清楚
2. 给出移动端最优 SQLite 表结构
3. 串起药品 OCR 与手语词汇联动流程
4. 说明 Android / Flutter 离线嵌入方式
5. 让文档可以直接写进项目开发文档和答辩材料

本文全部偏实操，不讲空理论。

## 2. 先给开发结论

### 2.1 数据源推荐等级

| 数据源 | 推荐等级 | 适合定位 | 结论 |
|---|---|---|---|
| NMPA | A | 官方校验源 | 用于药名、批准文号、生产企业校验 |
| DataSN 3万药品库 | A- | 离线主库候选 | 适合作为 SQLite 主数据来源，但必须确认授权 |
| 丁香园离线资源 | B | 结构参考源 | 适合研究离线包结构，不建议直接二次打包 |
| tngou 免费药品 API | D | 候选历史接口 | 当前不建议接入生产 |

### 2.2 你们项目最稳的落地组合

推荐组合：

- `NMPA` 负责标准药名和批准文号校验
- `DataSN` 或清洗后的公开药品数据负责离线主库
- `丁香园离线包` 负责给你们提供离线说明书架构参考
- `tngou` 暂时弃用

### 2.3 无障碍项目最稳主链路

```text
摄像头拍药盒
-> OCR 识别文字
-> 提取批准文号 / 通用名 / 商品名
-> 本地 SQLite 检索
-> 返回药品信息
-> 自动联动手语词汇或手语视频
-> TTS 播报 + 大字展示 + 震动提醒
```

## 3. 数据源一：NMPA 国家药监局数据查询

### 3.1 适合拿什么数据

适合拿的字段：

- 药品名称
- 批准文号
- 申请人 / 生产企业
- 批准日期
- 部分注册进度和公告信息

### 3.2 适合怎么用

适合用于：

- 校验药品标准名称
- 校验 OCR 识别出的批准文号
- 同步药品批准信息

不适合用于：

- 作为 App 在线实时主查询接口
- 直接当成现成的手机端离线说明书数据库

### 3.3 实操拿数方式

#### 方式 A：手工查

1. 打开 NMPA 政务服务入口
2. 进入药品相关查询页面
3. 按 `药品名称 / 批准文号 / 企业名称` 搜索
4. 手工整理核心字段到 Excel 或 CSV

#### 方式 B：脚本抓取网页

1. 抓取搜索结果页 HTML
2. 用解析脚本抽取表格字段
3. 输出为标准 CSV
4. 导入你们自己的 SQLite

### 3.4 可保留字段

建议最小字段集：

```text
generic_name
trade_name
approval_no
manufacturer
approval_date
source_url
```

### 3.5 数据转 CSV 流程

```text
NMPA 查询页 -> HTML 抓取 -> 解析字段 -> CSV
```

### 3.6 数据转 SQLite 流程

```text
CSV -> 清洗字段 -> 导入 drug_master -> 建批准文号索引
```

### 3.7 联网调用建议

NMPA 不适合当标准开放 REST API 来依赖，所以移动端不要直接把它当线上主查询接口。正确做法：

1. 服务端定时同步
2. 生成增量 CSV / JSON
3. 清洗后更新本地 SQLite

### 3.8 商用和风险说明

- 官方信息本身可信，但抓取方式要考虑页面变更风险
- 不适合直接在答辩里宣称“我们调用了官方开放 API”
- 更准确说法是“我们使用国家药监公开查询结果做标准校验”

### 3.9 项目适配等级

`A 级`

原因：

- 权威性高
- 适合做标准校验
- 对比赛展示说服力强

## 4. 数据源二：tngou 免费药品 API

### 4.1 当前核验结论

当前访问 `https://www.tngou.net/api/drug` 时，返回结果与标准药品 API 文档不一致，无法稳定确认其接口可用性、字段完整性和长期稳定性。

### 4.2 当前项目建议

直接结论：

- 不作为正式数据源
- 不作为比赛展示核心来源
- 不作为离线主库

### 4.3 如果你一定要继续验证

按下面顺序做：

1. 确认最新官方主页
2. 确认 API 文档是否还存在
3. 确认返回是否为 JSON
4. 确认是否限流或鉴权
5. 确认许可协议

只要有一项无法确认，就放弃接入。

### 4.4 项目适配等级

`D 级`

原因：

- 当前不可稳定验证
- 风险大于收益

## 5. 数据源三：DataSN 三万药品库

### 5.1 可拿到什么数据

页面信息显示它可提供大规模标准药品数据，常见字段包括：

- `generic_name`
- `trade_name`
- `maker`
- `composition`
- `indication`
- `specification`
- `usage_and_dosage`
- `adverse_reaction`
- `taboo`
- `attention`
- `interaction`
- `packet`
- `category`

### 5.2 适合怎么用

最适合用作：

- 本地离线 SQLite 主库
- 药品详情说明书来源
- 家庭常备药 / 慢病常用药底库

### 5.3 数据获取方式

常见方式：

1. 页面浏览字段和表结构
2. 使用页面暴露的 API 样例地址
3. 以 `JSON / CSV / Excel / XML / SQL` 等格式导出

### 5.4 建议获取顺序

1. 先拉取小样本 JSON
2. 验证字段是否稳定
3. 再导出 CSV
4. 本地清洗成你们自己的字段名
5. 最后导入 SQLite

### 5.5 数据清洗重点

重点清洗：

- 通用名统一
- 商品名去重
- 说明书长文本去多余空白
- 分类映射统一
- 别名抽取到独立表

### 5.6 转 CSV / SQLite 流程

```text
DataSN JSON/CSV -> 统一字段名 -> 去重 -> 建 alias -> 导入 SQLite
```

### 5.7 离线嵌入方案

推荐方式：

1. 在电脑端完成清洗
2. 只保留比赛版高频药
3. 生成 `drugs.db`
4. 放入 `assets/db/`
5. 首次启动复制到应用私有目录

### 5.8 联网调用方案

推荐联网只用于后台数据更新，不建议移动端前台直接查。

正确做法：

1. 服务端拉新数据
2. 清洗并生成新版本数据库
3. App 下载增量包或全量包

### 5.9 商用与版权风险

- 这是最需要提前确认授权的一类数据源
- 不要默认把它视为“公开网页可见就能直接商用”
- 比赛展示可以说明“基于公开可获取药品数据进行结构化整理”，但正式发版前必须确认授权边界

### 5.10 项目适配等级

`A- 级`

原因：

- 数据量大
- 字段完整
- 适合生成离线主库
- 但存在授权风险

## 6. 数据源四：丁香园用药助手离线资源

### 6.1 最有价值的点

它最值得你们学习的不是“药品内容本身”，而是“离线资源组织方式”。

从公开页面可确认：

- Android 端存在离线资源包
- 离线文件为 `extra.db`
- App 通过固定目录读取离线数据库

### 6.2 适合怎么用

适合：

- 研究表结构
- 研究离线数据库更新方式
- 研究说明书字段组织方式

不适合默认直接做：

- 直接把原 `extra.db` 打包进你们自己的 App
- 宣称自家 App 正式集成丁香园离线库

### 6.3 实操研究流程

1. 下载离线资源包
2. 复制到研究目录
3. 用 SQLite 工具打开
4. 查看 `.tables`
5. 查看 `.schema`
6. 记录哪些表适合借鉴

### 6.4 转 CSV 和转 SQLite 的方式

如果只是研究：

1. 用 SQLite 工具导表
2. 导出 CSV
3. 分析字段
4. 按你们自己的表结构重建数据库

### 6.5 联网使用建议

不建议当作联网 API 源；它更像现成离线包思路参考。

### 6.6 商用和版权风险

- 二次分发风险高
- 直接打包到你们作品中风险高
- 仅建议做结构借鉴，正式项目不要默认复用原始库

### 6.7 项目适配等级

`B 级`

原因：

- 架构参考价值高
- 数据直接使用风险高

## 7. 四个数据源统一整合策略

### 7.1 统一策略

不要让 App 同时直接依赖 4 个源，而要统一进你们自己的本地库。

推荐分工：

- `NMPA`：标准校验
- `DataSN`：主说明书数据
- `丁香园`：结构参考
- `tngou`：弃用

### 7.2 最终统一输出

统一产物只保留一个：

```text
drugs.db
```

数据库里至少包含：

- `drug_master`
- `drug_detail`
- `drug_sign_mapping`

## 8. 移动端最优 SQLite 表结构

### 8.1 设计目标

- 适配手机本地存储
- 支持 OCR 精准匹配
- 支持手语词汇和手语视频联动
- 支持后续增加风险规则

### 8.2 推荐表清单

1. `drug_master`
2. `drug_detail`
3. `drug_alias`
4. `drug_sign_mapping`
5. `drug_rule`

### 8.3 每张表职责

#### `drug_master`

保存最常用的主检索字段：

- 通用名
- 商品名
- 批准文号
- 厂商
- 剂型
- 规格
- 分类

#### `drug_detail`

保存说明书类大文本：

- 适应症
- 用法用量
- 禁忌
- 注意事项
- 不良反应
- 相互作用

#### `drug_alias`

保存别名和 OCR 容错词：

- 别名
- OCR 常错词
- 短名称

#### `drug_sign_mapping`

保存药品和手语资源映射：

- 标准手语词
- 手语视频路径
- 手语图片序列路径
- 手语拼写策略

#### `drug_rule`

保存风险提示规则：

- 高血压慎用
- 孕妇禁用
- 儿童剂量提醒

## 10. OCR -> 药品信息 -> 手语联动完整业务逻辑

### 10.1 正向流程：拍药盒到手语演示

```text
用户拍摄药盒
-> OCR 提取文字
-> 文本清洗
-> 提取批准文号 / 通用名 / 商品名
-> 查询 drug_master
-> 命中 drug_detail
-> 查询 drug_sign_mapping
-> 播放对应手语视频 / 图片序列
-> 同时显示药品详情、TTS 播报、震动提醒
```

### 10.2 检索优先级

固定顺序建议：

1. `approval_no`
2. `generic_name`
3. `trade_name`
4. `drug_alias.alias_name`
5. 模糊匹配

### 10.3 文本清洗规则

OCR 结果入库前先做：

1. 去多余空格
2. 统一全角半角
3. 统一大小写
4. 保留原始结果和清洗结果两份
5. 抽取药品常见后缀词

### 10.4 命中后 UI 输出内容

必须返回：

- 药品标准名称
- 用法用量
- 禁忌
- 注意事项
- 风险提示
- 手语资源
- TTS 播报文本

## 11. 反向流程：手语识别 -> 药品查询

### 11.1 反向链路

```text
前置摄像头采集手语
-> MediaPipe 提取手部关键点
-> LSTM / TFLite 识别词汇
-> 输出标准药品词或药品相关词
-> 映射到 drug_sign_mapping.sign_keyword
-> 反查 drug_id
-> 查询 drug_master + drug_detail
-> 返回药品信息
```

### 11.2 适合第一版的词汇范围

第一版不要做开放式药品手语自然语言翻译，只做这三类：

1. 常见药品名
2. 剂型词汇
3. 高频用药短语

示例：

- 阿莫西林
- 布洛芬
- 感冒药
- 降压药
- 片
- 胶囊
- 一天三次
- 饭后服用

### 11.3 手语资源组织建议

每个药品至少映射一种输出资源：

- `video_path`：标准手语视频
- `image_seq_path`：逐帧图示
- `spelling_mode`：无固定手语词时使用字母 / 拼音 / 分词拼手语

## 12. Android / Flutter 最简部署流程

### 12.1 数据库放置位置

推荐目录：

```text
app/src/main/assets/db/drugs.db
```

Flutter 推荐目录：

```text
assets/db/drugs.db
```

### 12.2 App 首次启动复制数据库

#### Android

1. 判断私有数据库目录是否存在 `drugs.db`
2. 若不存在，从 `assets/db/` 复制
3. 复制完成后再初始化 Room 或 SQLite

#### Flutter

1. 从 `rootBundle` 读取 `assets/db/drugs.db`
2. 写入 `getDatabasesPath()`
3. 再执行 `openDatabase()`

### 12.3 查询代码思路

#### Android

推荐层次：

```text
OCR -> ViewModel -> Repository -> Room DAO -> SQLite
```

查询方法至少要有：

- `searchByApprovalNo()`
- `searchByKeyword()`
- `getDrugDetail(drugId)`
- `getSignMapping(drugId)`

#### Flutter

推荐层次：

```text
OCR Service -> Repository -> sqflite DAO
```

查询方法与 Android 保持一致，方便双端统一。

## 13. 无障碍能力接入方案

### 13.1 语音播报

药品命中后，将以下字段拼成 TTS 文本：

- 药品名称
- 用法用量
- 禁忌
- 重要提醒

### 13.2 大字展示

页面必须优先展示：

1. 药品名称
2. 禁忌
3. 用法用量
4. 手语入口按钮

### 13.3 震动提醒

当 `drug_rule` 命中高风险规则时：

- 触发强震模式
- 弹出高对比度警示卡片
- 同步语音提醒

### 13.4 适配听障与低视力

- `听障`：文字 + 手语演示 + 强震
- `低视力`：大字 + TTS
- `双重障碍`：大字 + TTS + 强震一起给

### 14.1 数据端

1. 选定主数据源
2. 导出 CSV
3. 清洗字段
4. 生成 SQLite

### 14.2 Android / Flutter 端

1. 复制数据库
2. 封装 Repository
3. 接 OCR 结果查询
4. 接详情页显示
5. 接 TTS / 手语资源 / 震动

### 14.3 手语端

1. 先做药品高频词
2. 建 `drug_sign_mapping`
3. 先接视频或图示资源
4. 再接实时手语识别模型

## 15. 适合写进答辩稿的说法

- 我们采用“官方校验源 + 离线主库 + 手语映射库”三层数据架构
- 药盒识别后优先通过批准文号和标准药名进行本地检索
- 项目在离线状态下仍可完成药品识别、说明书查询和手语联动
- 针对听障和低视力用户，我们同时提供手语演示、语音播报、大字展示和震动提醒

## 16. 最终推荐方案

如果只看 4 天内能交付、还能在比赛里讲得稳，最推荐的落地方式是：

1. 用 `DataSN` 或公开清洗数据构建本地 SQLite 主库
2. 用 `NMPA` 做标准名和批准文号校验
3. 用自建 `drug_sign_mapping` 做药品到手语资源映射
4. 用 Android 先首发，Flutter 作为第二阶段扩展
5. 第一版只覆盖 100-500 个高频药品和 50-100 个高频手语词
