# 微光畅行 MVP 方案 v1.0

## 1. 项目背景

微光畅行定位为兼具公益属性的参赛项目，服务对象为个人用户与残联机构，优先解决听障用户在日常沟通、安全用药和强提醒场景中的高频痛点。首版产品需在 4 天内完成交付，因此方案必须优先保证社会价值呈现、可演示性和可试用性，而不是追求大而全。

## 2. 核心约束

- 服务对象：个人用户、残联机构。
- 项目定位：公益导向参赛项目。
- 用户研究：可接触真实听障用户，允许访谈和试用。
- 数据资源：无法获取医院和商业药品数据库，只能依赖公开数据源。
- 手语方向：优先支持中国手语。
- 交付周期：4 天内完成首版开发和展示。
- 优先级：社会价值 > 比赛展示效果 > 商业落地可行性。

## 3. 首版产品目标

首版产品不追求真正意义上的全自动连续手语翻译系统，而是构建一个可运行、可讲故事、可进行用户试用的无障碍助手 MVP，完成以下三个价值闭环：

1. 沟通闭环：听障用户可以快速表达高频需求，并把内容展示给听人。
2. 用药闭环：用户可拍摄药盒或说明书，快速得到药品名称、用药风险提示和语音播报。
3. 唤醒闭环：用户可以使用高强度震动提醒模式，解决传统声音闹钟不适用的问题。

## 4. MVP 范围定义

### 4.1 P0 功能

#### A. 小玉手语沟通模块

- 第一版目标：先完成高频短语级别的中国手语识别演示闭环。
- MVP 输入：摄像头视频输入先保留接口，界面侧先支持固定短语样例、演示结果区和文本转展示区。
- MVP 输出：
  - 大字字幕。
  - 常用语视频库占位能力。
  - 3D 手语人后续扩展说明，不纳入本次真实交付范围。
- 推荐首批高频短语：
  - 我要喝水
  - 我要去厕所
  - 我不舒服
  - 请帮帮我
  - 我要吃药
  - 请联系家人

#### B. OCR 药品识别模块

- 第一版目标：完成“识别药名 -> 匹配公开药品信息 -> 结合用户健康档案给出提醒”的基础流程。
- MVP 输入：
  - 药盒照片
  - 说明书照片
  - 手动搜索药名作为兜底方案
- MVP 输出：
  - 药品名称
  - 适应症
  - 禁忌/慎用信息
  - 针对高血压、糖尿病、孕妇、儿童、老年人、过敏史等标签给出风险提示
  - TTS 语音播报
- 注意事项：第一版定位为辅助提醒，不能表述为医疗诊断建议。

#### C. 强提醒闹钟模块

- 第一版目标：提供可展示、可试用的多段震动提醒能力。
- MVP 模式：
  - 渐强震动
  - 紧急爆发震动
  - 长循环提醒
- 技术边界：
  - 不承诺所有品牌都支持精细线性马达频率控制。
  - 优先采用 Android 标准振动 API + 预设波形。

### 4.2 暂缓功能

- 开放式连续中国手语实时翻译。
- 真实 3D 手语人驱动和骨骼动画。
- 医院级处方联动。
- 药物相互作用的专业医学推理。
- 鸿蒙原生全量适配。

## 5. 功能架构

### 5.1 端侧模块

- 首页：展示 3 个核心模块、用户价值和今日待办。
- 小玉模块：展示沟通状态、识别结果、常用表达和后续摄像头入口。
- 药品识别模块：展示拍照入口、药品识别结果、风险标签和播报按钮。
- 强提醒模块：展示不同震动模式和一键测试按钮。
- 个人健康档案：疾病史、过敏史、当前用药、紧急联系人。

### 5.2 云端/数据模块

- 公开数据抓取与清洗脚本。
- 药品信息标准化表。
- 风险规则配置表。
- 中国手语候选数据集索引表。
- 用户试用反馈记录表。

## 6. 公开数据策略

### 6.1 中国手语方向

首版不自己训练完整模型，而是采取“公开数据集调研 + 演示级交互闭环 + 后续模型接入接口预留”的策略。候选公开资源可从以下方向整理：

- 中国手语词级或句级公开视频数据集。
- 通用手部关键点与动态手势数据集，用于前期动作识别验证。
- 可公开引用的中国手语词表与高频表达清单。

当前建议优先关注的资源方向：

- 覆盖中国国家手语词汇的大规模词级数据集。
- 面向复杂环境的连续中国手语研究数据集。
- 通用手势和手部关键点公开数据集，作为冷启动补充。

### 6.2 药品识别方向

由于无法获取医院合作资源，首版采用“公开说明书 + 官方公开目录 + 手工整理的高频样本库”组合路线：

- 优先采集公开可检索的药品说明书文本。
- 整理常见家庭药、慢病常用药的名称、适应症、禁忌、慎用字段。
- 使用本地 JSON 先构建一个可演示的基础药品库。

推荐优先收录的药品范围：

- 感冒退烧类
- 止痛类
- 胃药类
- 高血压常用药
- 糖尿病常用药
- 抗过敏类

## 7. 用户研究计划

### 7.1 访谈对象

- 听障个人用户 3-5 人。
- 残联或相关机构工作人员 1-2 人。
- 若条件允许，加入 1-2 名低视力用户体验弱视模式。

### 7.2 访谈目标

- 确认沟通场景中最常用的高频表达。
- 确认用药信息获取中最让用户担心的点。
- 确认震动提醒的可接受强度和时长。

### 7.3 访谈问题提纲

1. 你在与陌生人沟通时最常遇到的障碍是什么？
2. 你最希望手机能帮你快速表达哪些内容？
3. 你在吃药时最担心哪些风险？
4. 你现在是如何设置闹钟或提醒的？
5. 你更喜欢大字、图片、视频还是语音播报？

### 7.4 试用验证任务

1. 在小玉模块中找到并表达“我要喝水”。
2. 在药品模块中查看某药是否适合高血压患者。
3. 在强提醒模块中启动一个高强度震动模式。

## 8. 4 天交付排期

### Day 1

- 明确 MVP 边界。
- 搭建 Android 首页和三大模块壳子。
- 定义药品基础数据结构和健康档案结构。
- 完成首轮用户访谈预约。

### Day 2

- 完成药品识别模块静态闭环。
- 完成强提醒模块震动模式体验。
- 整理首批高频中国手语表达清单。

### Day 3

- 完成小玉模块演示闭环。
- 完成弱视友好界面和大字模式优化。
- 邀请真实用户试用并记录反馈。

### Day 4

- 根据试用反馈修正文案和流程。
- 完成比赛讲述逻辑、演示脚本和答辩材料。
- 输出演示视频和版本说明。

## 9. 比赛展示策略

- 核心叙事：让听障用户“看得见、说得出、被叫醒、敢吃药”。
- 演示顺序：
  1. 首页介绍公益价值。
  2. 小玉模块展示高频表达。
  3. 药品识别展示风险提醒和语音播报。
  4. 强提醒展示震动测试。
- 评委关注点回答模板：
  - 为什么有社会价值。
  - 为什么 4 天内可交付。
  - 为什么即使没有医院资源也能做出有意义的 MVP。

## 10. 开发边界与风险控制

- 医疗相关提示统一使用“辅助判断，仅供参考”。
- 无法保证所有机型震动硬件表现一致，需要做兼容说明。
- 手语模块第一版不承诺开放语义级翻译，主打高频短语与后续扩展能力。
- 鸿蒙作为后续兼容目标，首版优先保证 Android 可演示、可试用。

## 11. 当前代码落地方向

本轮代码开发建议先完成以下内容：

1. 将空白模板改为微光畅行首页。
2. 增加三大模块的 MVP 演示界面。
3. 增加健康档案与风险提醒展示区。
4. 增加震动测试能力。
5. 保留手语识别、OCR、TTS 后续接入的接口说明。

## 12. 验收标准

- 打开 App 后能完整展示产品价值。
- 三大模块都能进入并完成演示流程。
- 文案体现公益定位、目标用户和辅助性质。
- 弱视用户能基本看清页面核心信息。
- 代码可编译，适合后续继续集成 OCR、相机和模型能力。
