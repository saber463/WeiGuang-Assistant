# 2026-05-16 CameraX 拍照入口接入说明

## 1. 文档目标

这份文档用于说明微光畅行药品模块本轮新增的 `CameraX 拍照入口` 能力。

本轮目标不是直接宣称已经完成完整药盒 OCR，而是先把真实相机入口接到应用里，为下一步 OCR 引擎接入打好底座。

当前已经完成的链路是：

```text
申请相机权限
-> 打开后置相机预览
-> 让用户对准药盒
-> 将当前画面接入现有识别占位链路
-> 继续走本地药品查询 / 风险分级 / TTS / 震动提醒
```

## 2. 为什么当前先做 CameraX 预览层

这样做有 3 个实际好处：

1. 先验证真实拍照入口是否稳定
2. 先把权限、生命周期、相机预览这些高风险基础设施跑通
3. 后续接 PaddleOCR 或其他 OCR 引擎时，不需要重做 UI 入口

## 3. 当前接入内容

### 3.1 构建层

当前已经在应用模块接入 CameraX 依赖：

- `camera-core`
- `camera-camera2`
- `camera-lifecycle`
- `camera-view`

### 3.2 权限层

当前已经在清单中增加：

- `android.permission.CAMERA`

### 3.3 页面层

当前药品页新增：

- `CameraX 拍照入口` 状态卡片
- `申请相机权限 / 打开后置相机` 按钮
- `关闭预览` 按钮
- `后置相机实时预览` 卡片
- `将当前相机画面接入识别链路` 按钮

## 4. 当前真实能力和边界

### 4.1 已完成的真实能力

当前这轮已经具备：

- 真正申请相机权限
- 真正打开后置相机实时预览
- 真正把拍照入口放进药品模块工作流

### 4.2 当前仍然是占位的部分

当前还没有完成：

- 从实时画面里真正提取文字
- 自动从药盒画面中识别药名和批准文号
- 自动把相机帧送进 OCR 引擎

所以当前页面上的“接入识别链路”按钮，本质上是：

- 用真实 CameraX 预览验证拍照入口
- 再用当前输入框关键词承接后续查询链路

这是一种刻意保守的做法，目的就是保证 4 天版本稳定可演示，而不是用半成品 OCR 冒充已完成功能。

## 5. 当前页面交互逻辑

### 5.1 首次进入

药品页默认不会强行打开相机。

用户需要主动点击：

- `申请相机权限`
- 或 `打开后置相机`

### 5.2 权限通过后

页面会显示：

- 相机权限已就绪
- 后置相机实时预览

### 5.3 用户对准药盒后

用户可以点击：

- `将当前相机画面接入识别链路`

当前版本会把这一步视为：

- 已从真实拍照入口进入
- OCR 引擎暂未接入
- 先用当前输入框关键词继续跑通结果页和提醒链路

## 6. 为什么这样设计更安全

### 6.1 对用户更诚实

当前页面没有假装“已经识别成功”，而是明确说明：

- 相机入口已接通
- OCR 仍待下一步接入

### 6.2 对比赛演示更稳

这样可以避免在现场因为 OCR 模型、机型兼容、权限时序等问题导致整条链路失效。

### 6.3 对后续开发更顺

后续真正接 OCR 时，只需要继续补：

- 相机帧采集
- 文字识别
- 关键词提取

药品查询、风险分级、震动提醒、TTS 和手语联动都能复用。

## 7. 下一步推荐接法

最推荐的下一步技术路线：

```text
CameraX Preview / ImageAnalysis
-> OCR 引擎识别原始文本
-> 提取批准文号 / 通用名 / 商品名
-> 调用现有 launchMedicineSearch(...)
```

## 8. 建议下一步

最建议继续推进的 3 件事：

1. 接入 `ImageAnalysis` 用例，把实时画面帧交给 OCR
2. 增加批准文号优先匹配
3. 增加拍照成功后的裁剪和识别状态反馈
