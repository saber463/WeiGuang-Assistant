# 2026-05-19 真机体验：拍照冻结识别优化说明

## 1. 文档目标

本轮目标聚焦“真机体验”，把药品页从偏工程调试的实时流识别，升级为更符合用户直觉的流程：

```text
打开相机
-> 对准药盒
-> 拍照冻结识别（单帧 OCR）
-> 用户确认识别结果
-> 查询本地药品库 / 风险提示 / TTS / 震动
```

核心指标是“稳定、可控、可解释”，降低实时流抖动带来的误判和跳变。

## 2. 为什么要做拍照冻结识别

实时流 OCR 在真机上常见问题：

- 画面轻微抖动导致文本变化
- 识别结果在不同帧之间跳变
- 用户难以判断“当前看到的是最终结果还是暂态”

拍照冻结识别的好处：

- 让用户用“拍一下”表达“我现在要结果”
- OCR 在单帧上运行，结果更稳定、可复核
- 引入“确认再查询”环节，降低误触发风险提示的概率

## 3. 页面层交互变化

### 3.1 新增识别状态反馈

药品页在相机区域新增：

- `当前识别状态` 卡片
- `拍摄建议 / 推荐距离 / 推荐动作` 指引卡片

用来把“系统正在做什么”明确告诉用户，减少探索成本。

### 3.2 新增拍照冻结识别按钮

相机预览开启后，提供两条路径：

- `拍照冻结识别`：真机推荐路径
- `直接用实时结果`：应急兜底路径

### 3.3 新增识别结果确认弹层

点击 `拍照冻结识别` 后弹出确认层，展示：

- 单帧 OCR 原文
- 提取策略
- 批准文号
- 建议查询词

用户可选：

- `确认并查询`：进入本地药品检索链路
- `继续重拍`：返回预览继续对准

## 4. 技术实现要点

### 4.1 CameraX 用例组合

相机绑定用例从：

- `Preview + ImageAnalysis`

升级为：

- `Preview + ImageAnalysis + ImageCapture`

其中：

- `ImageAnalysis` 继续用于实时辅助对准
- `ImageCapture` 用于单帧冻结识别

### 4.2 分析暂停机制

当确认弹层打开时，实时分析暂停：

- 避免后台继续刷新结果导致“确认内容被打断”
- 减少设备资源消耗

### 4.3 单帧 OCR 处理

拍照成功后直接把 `ImageProxy` 送入 ML Kit：

- 成功：走同一套 `批准文号 -> 词典 -> 回退中文候选` 的提取策略
- 失败：给出更具体的失败提示（光线、反光、距离等）

## 5. 真机验收标准（建议）

建议按下面标准验收：

- 首次安装后能正常打开，权限申请不异常
- 打开相机后能稳定显示预览画面
- 对准药盒后，点击 `拍照冻结识别`，3 秒内给出单帧 OCR 原文
- 单帧识别结果在弹层内不跳变
- 点击 `确认并查询` 后可命中本地药品库或明确提示未命中

## 6. 当前边界

本轮仍未包含：

- 识别区域裁剪与框选
- 拍照后图片预览
- 置信度与多候选展示
- 不同机型相机参数与对焦优化

这些属于下一阶段的体验深化项。

## 7. 数据库兼容要点

本项目使用 `createFromAsset("db/drugs.db")` 加载预置离线库。

真机闪退且日志包含：

- `Pre-packaged database has an invalid schema`

通常意味着：

- `Room Entity` 的字段/约束
- `docs/sql/drug_offline_schema.sql` 的建表约束
- `tools/build_seed_db.py` 生成出来的 `app/src/main/assets/db/drugs.db` 实际结构

三者之间发生了漂移。

本轮修复原则：

- 统一以 `docs/sql/drug_offline_schema.sql` 为准生成 `drugs.db`
- 关键表主键列必须显式 `NOT NULL`
- 每次改 `SQL` 后必须重新运行：

```bash
python tools/build_seed_db.py
```

再重新打包 APK 上机验证。
