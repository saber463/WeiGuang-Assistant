# 2026-05-16 OCR 查询入口接入说明

## 1. 文档目标

这份文档用于说明微光畅行药品模块本轮新增的 `OCR 查询入口` 能力。

本轮目标不是直接宣称已经完成完整拍照识别，而是先把下面这条核心链路打通：

```text
OCR 结果文本
-> 药品关键词提取
-> 本地药品库查询
-> 风险分级
-> 手语联动
-> 风险提醒反馈
```

这样做的价值是：

- 先验证药品 OCR 结果进入业务链路是否通顺
- 后续接 CameraX、PaddleOCR 或其他 OCR 引擎时，不需要重写药品查询流程
- 比赛演示时可以明确展示“我们已经打通 OCR 结果接入层”

## 2. 当前接入方式

### 2.1 页面新增模块

当前药品页新增了 `OCR 结果入口` 区域，包含：

- OCR 预览文本卡片
- 3 条药盒 OCR 示例
- 1 个“把当前输入当作 OCR 结果接入”按钮

### 2.2 当前支持的两种接入方式

#### 方式一：OCR 示例输入

页面内置了 3 条示例药盒 OCR 文本：

- 芬必得 / 布洛芬缓释胶囊
- 阿莫仙 / 阿莫西林胶囊
- 格华止 / 盐酸二甲双胍片

点击后会自动完成：

1. 更新 OCR 预览文本
2. 取出提取关键词
3. 发起本地药品查询
4. 进入风险分级与联动提醒流程

#### 方式二：OCR 手动录入

用户可以把识别得到的药盒文字手动粘贴到输入框，再点击：

- `把当前输入当作 OCR 结果接入`

这样可以先模拟未来真实 OCR 返回的文本结果。

## 3. 当前代码设计

### 3.1 统一查询入口

当前药品页把查询逻辑统一收口到：

- `launchMedicineSearch(triggerRiskAlert, incomingKeyword, sourceLabel)`

这个方法负责：

1. 确定最终查询关键词
2. 调用 Repository 查询本地药品库
3. 生成风险播报文案
4. 生成风险联动反馈
5. 触发高风险或中风险震动提醒

### 3.2 OCR 与手动输入共用同一条路径

这意味着当前有 3 类来源都能进入同一链路：

- 手动输入
- OCR 示例输入
- OCR 手动录入

后续新增真实 OCR 时，只需要把识别出的文字继续传给 `incomingKeyword` 即可。

## 4. 当前页面效果

用户现在可以在药品页清楚看到：

- 当前 OCR 预览文本
- 这次查询来自手动输入还是 OCR 输入
- 命中的药品结果
- 风险等级
- 手语联动结果
- 当前是否触发了风险联动提醒

## 5. 为什么当前先这样做

### 5.1 降低首版交付风险

如果直接上真实相机和 OCR SDK，会同时叠加这些不确定性：

- 相机权限
- 相机预览
- OCR SDK 依赖体积
- 端侧模型初始化
- 机型兼容问题

而当前版本先把 `OCR 结果接入口` 打通，可以保证 4 天交付内先拿到稳定演示链路。

### 5.2 方便后续平滑升级

后续接入真实 OCR 时，只需要新增：

- 相机采集
- OCR 模型推理
- 关键词提取策略

药品查询、风险分级、手语联动、震动提醒这几层可以继续复用。

## 6. 下一步怎么接真实 OCR

最推荐的接法如下：

### 6.1 Android 原生接法

```text
CameraX 采集画面
-> OCR SDK 返回原始文本
-> 提取药名 / 批准文号 / 商品名
-> 调用 launchMedicineSearch(...)
```

### 6.2 关键词提取优先级

建议优先按以下顺序提取：

1. 批准文号
2. 通用名
3. 商品名
4. 常见别名

### 6.3 正式接入后的页面状态

接入真实 OCR 后，建议把当前 `OCR 示例输入` 保留为：

- 演示兜底
- 调试入口
- 无相机权限场景下的备选方案

## 7. 当前边界

当前版本仍然有这些限制：

- 还没有接真实相机
- 还没有接 PaddleOCR 或 Tesseract
- 还没有自动从 OCR 长文本中做复杂实体抽取
- 当前关键词提取还是以演示样本和手动录入为主

## 8. 建议下一步

最推荐直接继续推进的两步：

1. 接入真实 OCR SDK 或 CameraX 拍照入口
2. 增加批准文号优先匹配和 OCR 容错规则
