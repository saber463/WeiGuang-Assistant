# 方案 B 文档基线补齐计划

## Summary

基于当前仓库现状与已确认的“方案 B”原则，先补齐一套正式研发文档基线，再进入新功能开发。

本计划的目标不是改代码，而是一次性补齐以下 8 份 Markdown 文档，并统一它们之间的边界、命名、引用关系和技术口径：

1. `需求规格说明书`
2. `前后端分离开发计划`
3. `Android 客户端架构设计文档`
4. `后端架构设计文档`
5. `开发经验与教训文档`
6. `接口设计规范文档`
7. `数据设计文档`
8. `数据库设计文档`

文档总原则如下：

- 以 `docs/2026-05-19-微光畅行-最终定稿完整版技术栈.md` 作为技术基线。
- 以前期已有 MVP、数据层、药品离线库文档作为事实输入，而不是直接复用为正式总文档。
- 采用“本地优先 + 云端不碰用户隐私”的总体架构。
- 前端定义锁定为 `Android 客户端`，不单独新增 Web 前端架构文档。
- 后端定义为 `资源与配置服务 + 管理后台 + 数据处理平台`，不承接用户原始敏感数据的实时处理。

### 3. 当前架构边界事实

从现有文档可确认：

- 当前落地重点仍在 Android 客户端。
- 当前仓库没有独立后端工程，也没有独立管理后台工程。
- 当前已经存在本地药品库、CSV、SQL、Room、离线库构建脚本等离线数据链路基础。
- 当前技术栈文档明确了未来全量功能范围，已超出 MVP 三模块。

因此，新文档必须同时满足两个要求：

- 既能解释当前仓库现状。
- 又能为后续全量功能扩展提供正式设计基线。

## Assumptions & Decisions

### 1. 已确认决策

- 方案采用 `B：本地优先 + 云端不碰用户隐私`。
- 文档范围按“全量功能”编写，不按 MVP 缩减。
- “前端架构文档”中的前端明确为 `Android 客户端`。
- 系统整体形态为：
  - `Android 客户端`
  - `业务 API`
  - `管理后台`
  - `数据处理平台`

### 2. 本计划内直接锁定的写作口径

为避免执行时继续做高层选择，文档写作统一采用以下口径：

- 用户原始敏感数据默认不上传云端，包括：
  - 原始语音
  - 原始图片
  - 原始手势视频
  - 健康档案明文
  - 端侧识别中间结果
- 云端只负责：
  - 离线资源版本管理
  - 药品库/词库/模型包/规则包生产与分发
  - 后台配置管理
  - 内容审核与发布
  - 非敏感版本信息、资源清单、更新策略
- Android 客户端负责：
  - 端侧识别
  - 本地规则判断
  - 本地数据存储
  - 本地无障碍提醒
  - 本地隐私保护

### 3. 推荐后端技术路线

后端架构文档按以下推荐方案撰写：

- 业务 API / 管理后台后端：`Java 17 + Spring Boot 3`
- 数据库：`PostgreSQL`
- 缓存与任务协调：`Redis`
- 对象存储：`MinIO` 或兼容对象存储
- 管理后台前端仅作为后端文档中的配套子系统说明，不单独输出前端架构文档
- 数据处理平台：以现有 `tools/build_seed_db.py` 为起点，扩展为 `Python` 数据加工与资源构建流水线

采用这套推荐方案的原因：

- 与当前 `F:\java\weiguangplus` 的 Java/Kotlin 技术背景一致。
- 便于统一团队语言与后续 API/数据文档表述。
- 与现有 Python 数据脚本现状兼容，不需要在文档里强行推翻已有数据处理方式。

#### 2.1 `需求规格说明书`

文件：`docs/2026-05-19-微光畅行-需求规格说明书.md`

- 项目背景、目标用户、使用场景、术语定义

写法要求：

- 以“用户问题 -> 系统能力 -> 验收结果”的方式展开
- 明确把全量功能拆为正式功能域：
  - 双向手语互通
